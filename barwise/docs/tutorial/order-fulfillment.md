A note before you start: each step shows you a *problem first* -- often a
concrete population the model-so-far wrongly allows -- and only then the

This feels harder than reading definitions; it is meant to. If you have

early steps are where those habits mislead.

This tutorial builds one small model -- order fulfillment: customers, orders, products, statuses -- by walking the Conceptual Schema Design Procedure (CSDP), the seven-step method ORM ships with. Every step starts from a defect the model still has, and most defects are not described but *generated*: barwise computes the exact population the current model wrongly allows, and the step's concept is whatever rules it out. By the end you will have watched a model earn each of its constraints.

## Step 1: From familiar examples to elementary facts

*CSDP step 1.*

### The problem

Here is how the fulfillment team talks: "Ines placed order 501. Order 501 includes the espresso machine and the grinder. It is still open." Nothing here is a table or a column; it is sentences about individual things. The first CSDP step is to keep it that way: restate the examples as *elementary facts* -- sentences that cannot be split without losing information -- and name the kinds of things they mention. "Ines placed order 501" mentions a Customer and an Order; splitting it loses the fact entirely, so it is elementary.

### The concept

An ORM model starts as a set of fact types -- sentence patterns with holes -- not as tables. Each hole is a *role* played by an *object type*, and each object type needs a *reference scheme*: how a single instance is identified (a customer number, an order number, a product code). Write the pattern both ways when it reads naturally ("Customer places Order" / "Order is placed by Customer"); these *readings* are the model's contract with the domain expert, who can check a sentence but not a schema. Note what is missing on purpose: no keys, no foreign keys, no nulls. Those are relational concerns; here there are only facts.

### The model so far

```
Customer places Order
Order is placed by Customer
Order includes Product
Product is included in Order
Order has OrderStatus
```

## Step 2: Populate the fact types and look at what they allow

*CSDP step 2.*

Builds on: [Step 1: From familiar examples to elementary facts](#step-1-from-familiar-examples-to-elementary-facts).

### The problem

A fact type without sample facts is a guess. The second CSDP step is the *population check*: fill each fact type with real examples and read every row aloud as a sentence. Do it here and something is off: the sample data records both "C-1001 places O-501" and "C-1002 places O-501" -- one order placed by two different customers. Every row reads fine on its own. The problem is not in any row; it is that nothing yet says which *combinations* of rows are impossible.

### The concept

Populations are the model's test data, and reading them aloud is the cheapest validation ORM has. A population that looks wrong but is allowed is the signal that a *constraint* is missing -- constraints are exactly "which populations are impossible." This step also covers the CSDP's early hygiene checks: are two object types really the same kind of thing under different names (Product vs. Item), and is any "fact" really derivable from others? Settle those before constraining. From here on, every step is provoked by a population the model still allows.

### The model so far

```
Customer places Order
Order is placed by Customer
Order includes Product
Product is included in Order
Order has OrderStatus
```

## Step 3: Each order has one placer: internal uniqueness

*CSDP step 4.*

Builds on: [Step 2: Populate the fact types and look at what they allow](#step-2-populate-the-fact-types-and-look-at-what-they-allow).

### The problem

Until this step, nothing in the model forbids the following
population -- the tool derives it mechanically from the constraint you
are about to add:

> Rules out: two facts of Customer places Order that agree on Order -- e.g. {Customer=Customer#1, Order=Order#1}; {Customer=Customer#2, Order=Order#1}

*(motivation generated from the model)*

### The concept

A *uniqueness constraint* over a role says: in the population, each instance plays that role at most once. Spanning just the Order role of "Customer places Order", it makes the offending pair of rows from the last step impossible -- one order, one placer -- while leaving a customer free to place many orders. This is the constraint that fixes the fact type's *multiplicity* (many-to-one), and it is the single most common constraint in any model. Verbalized, it reads back as the business rule the team would actually say: "each Order is placed by at most one Customer."

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Order includes Product
Product is included in Order
Order has OrderStatus
```

## Step 4: Many-to-many still needs uniqueness: the spanning constraint

*CSDP step 4.*

Builds on: [Step 3: Each order has one placer: internal uniqueness](#step-3-each-order-has-one-placer-internal-uniqueness).

### The problem

Until this step, nothing in the model forbids the following
population -- the tool derives it mechanically from the constraint you
are about to add:

> Rules out: two facts of Order includes Product that agree on Order, Product -- e.g. {Order=Order#1, Product=Product#1}; {Order=Order#1, Product=Product#1}

*(motivation generated from the model)*

### The concept

"Order includes Product" is genuinely many-to-many: an order holds many products, a product appears in many orders. It is tempting to conclude no uniqueness applies -- but then the same row could be recorded twice, as the generated population shows. The fix is a uniqueness constraint *spanning both roles*: each (Order, Product) combination at most once. Every elementary fact type carries some uniqueness constraint; what varies is how many roles it spans. The same move gives "Order has OrderStatus" its one-status-per-order rule.

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Order includes Product
Product is included in Order
Each combination of Order and Product is unique in Order includes Product.
Order has OrderStatus
Each Order has at most one OrderStatus.
```

## Step 5: No order from nowhere: the mandatory role

*CSDP step 5.*

Builds on: [Step 3: Each order has one placer: internal uniqueness](#step-3-each-order-has-one-placer-internal-uniqueness).

### The problem

Until this step, nothing in the model forbids the following
population -- the tool derives it mechanically from the constraint you
are about to add:

> Rules out: a Order that exists but never plays "Customer places Order" -- e.g. Order#1 appears in Order includes Product but not in Customer places Order

*(motivation generated from the model)*

### The concept

Uniqueness says "at most"; *mandatory* says "at least". Without it, an order can exist in the model -- appear in "Order includes Product", carry a status -- while playing no role in "Customer places Order" at all: an order nobody placed. Marking the Order role mandatory closes that gap: every order that exists anywhere must appear here. Together the pair reads "each Order is placed by exactly one Customer" -- and note the asymmetry: Customer's role stays optional, because a customer with no current orders is fine. Deciding which roles are mandatory is a business question, not a formality.

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Each Order is placed by at least one Customer.
Order includes Product
Product is included in Order
Each combination of Order and Product is unique in Order includes Product.
Order has OrderStatus
Each Order has at most one OrderStatus.
```

## Step 6: Only these statuses: the value constraint

*CSDP step 6.*

Builds on: [Step 5: No order from nowhere: the mandatory role](#step-5-no-order-from-nowhere-the-mandatory-role).

### The problem

Until this step, nothing in the model forbids the following
population -- the tool derives it mechanically from the constraint you
are about to add:

> Rules out: OrderStatus taking a value outside {open, shipped, cancelled} -- e.g. {Order=Order#1, OrderStatus=OrderStatus#invalid}

*(motivation generated from the model)*

### The concept

OrderStatus is a *value type*: its instances are the values themselves, so the type is constrained by listing them. A *value constraint* on the status role pins the population to {open, shipped, cancelled} -- anything else is not a status, it is a typo. Value constraints are how a model refuses the "stringly typed" failure mode: the legal vocabulary is part of the schema, visible to the domain expert in the verbalization, not buried in application code.

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Each Order is placed by at least one Customer.
Order includes Product
Product is included in Order
Each combination of Order and Product is unique in Order includes Product.
Order has OrderStatus
Each Order has at most one OrderStatus.
The possible values of OrderStatus are: {'open', 'shipped', 'cancelled'}.
```

## Step 7: Some orders are special: subtyping

*CSDP step 6.*

Builds on: [Step 6: Only these statuses: the value constraint](#step-6-only-these-statuses-the-value-constraint).

### The problem

The team flags some orders for expedited handling, and only those get assigned to a courier. Where does "is assigned to Courier" attach? On Order, the model quietly claims any order may have a courier -- false. A status value "priority" says nothing about the courier rule. What the domain is telling us is that a *kind of order* exists with facts of its own.

### The concept

A *subtype* is an object type whose instances are a subset of another's: every PriorityOrder is an Order, identified the same way, inheriting every Order fact type -- and roles that apply only to the subtype attach to the subtype. "PriorityOrder is assigned to Courier" now says exactly what the business said: couriers are for priority orders, full stop. Subtype when a subset of instances plays roles the rest cannot; use a value (like OrderStatus) when it is just a changing label with no facts of its own.

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Each Order is placed by at least one Customer.
Order includes Product
Product is included in Order
Each combination of Order and Product is unique in Order includes Product.
Order has OrderStatus
Each Order has at most one OrderStatus.
The possible values of OrderStatus are: {'open', 'shipped', 'cancelled'}.
PriorityOrder is assigned to Courier
Each PriorityOrder is assigned to at most one Courier.
PriorityOrder is a subtype of Order.
```

## Step 8: At most five products: the frequency constraint

*CSDP step 7.*

Builds on: [Step 4: Many-to-many still needs uniqueness: the spanning constraint](#step-4-many-to-many-still-needs-uniqueness-the-spanning-constraint), [Step 7: Some orders are special: subtyping](#step-7-some-orders-are-special-subtyping).

### The problem

Until this step, nothing in the model forbids the following
population -- the tool derives it mechanically from the constraint you
are about to add:

> Rules out: the same Order in Order includes Product more than 5 time(s) -- e.g. {Order=Order#1, Product=Product#1}; {Order=Order#1, Product=Product#2}; {Order=Order#1, Product=Product#3}; {Order=Order#1, Product=Product#4}; {Order=Order#1, Product=Product#5}; {Order=Order#1, Product=Product#6}

*(motivation generated from the model)*

### The concept

The warehouse packs at most five distinct products per order; bigger requests are split. Uniqueness cannot say this -- it only forbids exact repeats. A *frequency constraint* bounds how many times an instance may play a role: here, an order appears in "Order includes Product" between one and five times. This is the CSDP's final family -- the "other constraints" pass (frequency, ring, and friends) that captures the numeric and structural rules the earlier passes could not express. The model is now complete enough to hand to the relational mapper -- and every constraint in it was earned by a population it rules out.

### The model so far

```
Customer places Order
Order is placed by Customer
Each Order is placed by at most one Customer.
Each Order is placed by at least one Customer.
Order includes Product
Product is included in Order
Each combination of Order and Product is unique in Order includes Product.
Each Order includes at least 1 and at most 5 Product.
Order has OrderStatus
Each Order has at most one OrderStatus.
The possible values of OrderStatus are: {'open', 'shipped', 'cancelled'}.
PriorityOrder is assigned to Courier
Each PriorityOrder is assigned to at most one Courier.
PriorityOrder is a subtype of Order.
```
