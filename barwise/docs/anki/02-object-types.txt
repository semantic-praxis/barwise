What are the two kinds of ObjectType in ORM?	<b>Entity type</b> -- a concept identified by a reference scheme (e.g. Person, Order).<br><b>Value type</b> -- a self-identifying lexical object (e.g. a string or number like a name or amount).<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What makes a value type "self-identifying"?	The value denotes itself: the string 'Ada' or the number 42 needs no separate identifier. A value type carries no reference scheme.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What must every entity type have that a value type does not?	A <b>reference scheme</b> -- a way to identify its instances, relating the entity type to one or more value types that name it. (A structural validation rule: entity types have a reference scheme.)<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What is a <i>reference mode</i>, and give the one Barwise writes as <code>reference_mode: id</code>?	A reference mode is the shorthand for how an entity type is identified by a value type, e.g. Person(.Nr) or Product(.code). Barwise's <code>id</code> mode means the entity is identified by an opaque surrogate id.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
Why prefer a reference scheme over just "an id column" when modeling conceptually?	Because the reference scheme states, in the model, <i>which value type identifies the entity and how a human refers to it</i>. The physical id/key is a downstream mapping decision, not the conceptual identity.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What is a <i>compound reference scheme</i>?	An entity type identified by a combination of values rather than one, e.g. a Room identified by (Building, RoomNumber) together. It maps to an external/compound uniqueness constraint over the identifying facts.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What is objectification (a nested / objectified fact type)?	Treating a fact type as though it were an entity type, so it can itself play roles in other facts. Example: the fact "Student enrolled in Course" is objectified as "Enrollment", which then "has Grade".<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
When do you reach for objectification?	When a relationship itself needs to carry further facts or be referenced -- when you want to say something <i>about the fact</i>. If Enrollment needs a grade and a date, objectify "Student enrolled in Course".<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
Every model element in Barwise carries a stable opaque UUID assigned at creation. Name two things that enables.	1. Renaming an element without breaking references to it.<br>2. Diffing and merging model files, and tracing downstream artifacts (DDL, dbt tests) back to the source element.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
True or false: in ORM you decide up front whether "Email" is an attribute or an entity.	False -- there are no attributes. "Email" is a value type (or entity type) that plays a role in a fact type. If it later needs its own facts or constraints, nothing is restructured.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
What is a <i>definition</i> attached to an object type, and what larger thing does it build?	A natural-language statement of what the object type means. Collected across the model, definitions form the domain's <b>ubiquitous language</b> -- the shared, agreed vocabulary.<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
A completeness warning fires for an object type with no definition. Why is that worth flagging?	Because an undefined object type has no agreed meaning -- it is a name without a concept. The definition is what lets two teams confirm they mean the same thing by "Customer".<br><br><i>Read more: Halpin & Morgan 3rd ed. -- section 5.3 (reference schemes), 6.3 (value and independent types), 10.5 (objectification).</i>
