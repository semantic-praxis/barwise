When should you split one .orm.yaml model into a multi-file project?	When the single file is the problem: it is too big to hold in your head, different teams own different parts and collide on every merge, the same word means different things to different teams, or you only ever validate/diagram a slice. If none of these bite, stay with one file.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
What is a <b>bounded context</b> in the ORM project sense, and how do you find them?	A part of the model with its own vocabulary and a clear owner. You find them by grouping object types by the <i>language people use</i> around them -- not by database tables or technical convenience.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
Name the three file types in a Barwise multi-file project and what each holds.	<code>.orm-project.yaml</code> -- the manifest (lists domains and mappings). <code>.orm.yaml</code> -- one domain model per bounded context. <code>.map.yaml</code> -- one context mapping per seam between contexts.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
What is a <b>seam</b> in a multi-context project?	A place where two contexts both touch a concept (e.g. an auction listing referring to a catalog asset). Seams are expected; the <code>.map.yaml</code> files document them.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
How does a cross-domain reference name an object type, and why the qualification?	As <code>context:ObjectType</code>, e.g. <code>auctions:Auction</code>. The qualifier keeps <code>auctions:Auction</code> and <code>billing:Auction</code> unambiguous even when both contexts define a type with the same name.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
What is a <b>shadow</b> object type?	When two contexts share an object type, the owner keeps the real definition and the other context gets a copy marked with <code>source_context</code>. The shadow signals "owned elsewhere" so readers know where the definition lives.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
Name the three context-mapping patterns Barwise supports (from the DDD catalogue).	<code>shared_kernel</code> (both contexts genuinely share one definition), <code>published_language</code> (a conformed definition multiple contexts agree to), and <code>anticorruption_layer</code> (a translation boundary with explicit transformation).<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
When two contexts use the same term with different meanings, which pattern and which record capture it?	The <code>anticorruption_layer</code> pattern, with a <code>semantic_conflict</code> recording the term, each side's meaning, and the resolution.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
When <code>barwise project split</code> runs, why might it drop a constraint, and what should you do?	A uniqueness, subset, or equality constraint whose roles span two contexts cannot live in a single-file model, so the split drops it and warns. If it matters, re-express it within one context or record it in the mapping.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
What is a <b>data product</b> in Barwise, structurally?	An <code>.orm.yaml</code> domain model that (1) declares <code>depends_on</code> source domains and mappings, and (2) introduces analytical-only concepts (metrics, KPIs, grain, cohorts). It composes domain concepts without owning them -- no new file format needed.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
How is an analytical metric like "Lifetime Revenue" modeled in a data product?	As a derived fact type with a definition that traces to its source fact types. A grain like "one row per customer per month" is a documented constraint on the product's primary fact types. Analytical concepts get the same validation and verbalization as any fact type.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
The split is deterministic. What does that let you treat the split output as?	A to-do list: the same config always produces the same project, so you tighten the config against the warnings (inferred homes, generated mappings, dropped constraints) rather than hand-editing the output.<br><br><i>Read more: barwise ORM_PROJECT_GUIDE.md and ARCHITECTURE.md sections 3.1.4-3.1.5; DDD context mapping (Evans).</i>
