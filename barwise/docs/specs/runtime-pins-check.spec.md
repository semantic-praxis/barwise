## Principle

`docs/adr/pinned-runtimes.md` pins Node in `.nvmrc` and Python's minor
in `.python-version`, and says to verify the interpreter that ran, not
the file that asked. Nothing checks any of the three. This is
`deterministic-guards.spec.md` workstream 4 (`check:pins`), approved and
never grounded; this spec grounds it for the two runtimes and leaves its
runner-image clause to an open decision.

## The reading this spec starts from (main at 478d0fd8)

- All four workflows set Node with `node-version-file: .nvmrc` and none
  names a literal version; nothing stops one from doing so
  (barwise-ym8.q89). `README.md` says "currently 26.7.0", matching
  `.nvmrc` with nothing checking it (barwise-8hs). `engines.node` is
  `>=26.0.0`. The session hook reads `.nvmrc`.
- `.python-version` (3.13) sits at the repository root. Measured here
  with uv 0.11.32 in a scratch project: uv reads a `.python-version` in
  the project directory and ignores one in its parent, so from
  `barwise/` the pin is never seen and the interpreter floats within
  `requires-python = ">=3.13"` (barwise-g32, barwise-ym8.52y).
- No gate reads back the Node or Python that ran; `ci:local` and the
  hooks do not (barwise-1045, barwise-ym8.eq3).
- CI's unguarded "Python toolchain (uv)" step installs uv, runs `uv
  python install` in `barwise/` and syncs; every later step has both
  runtimes.

## Scope

1. **`barwise/.python-version`**, a copy of the root file beside
   `pyproject.toml`, where uv reads it. Decision 2's "beside `.nvmrc`"
   stays true; the copy is a must-agree pair that `check:pins` holds.
2. **`check:pins`**, findings (exit 1):
   - a workflow `actions/setup-node` step without `node-version-file:
     .nvmrc`, or with `node-version`;
   - `README.md`'s "currently X" differing from `.nvmrc`;
   - `engines.node`'s floor naming another major than `.nvmrc`;
   - the session hook not reading `.nvmrc`;
   - `barwise/.python-version` differing from the root file, or either
     naming more than a minor (`3.13`, never `3.13.12`, per decision 2);
   - `requires-python`'s floor naming another minor than the pin.

   Refusals (exit 2), reading back what runs:
   - the Node running the gate on another major than `.nvmrc`;
   - the Python that `uv run --frozen --project barwise` starts on
     another minor than the pin, or uv absent or failing.

   The exact versions that ran are printed on every run, so a reading
   is attributable. A Node patch differing from `.nvmrc` is printed,
   not refused (open decision 2).
3. **Wiring.** A `ci.yml` step with no `if:`, after the Python toolchain
   step; `ci:local` derives it from `ci.yml`, so the pre-push hook runs
   it.

Out of scope: the runner image (`runs-on: ubuntu-latest`, open decision
1); uv's own version (python-uv-widened WS4); whether `uv.lock` is a
single resolution (barwise-g32's other half).

## Alternatives considered

- **Moving `.python-version` into `barwise/`.** One file, read by uv.
  But decision 2 says "beside `.nvmrc`", so it rewords a decision; and
  CI's comment and the README point at the root. Rejected for a checked
  copy; the owner may prefer the move (open decision 3).
- **`requires-python = "==3.13.*"`.** uv would refuse other minors on
  its own. It changes `uv.lock`'s header, and the lock would be
  regenerated by a uv (0.11.32 here) older than CI's 0.12.7. Rejected
  until uv is pinned locally (python-uv-widened WS4).
- **A parity-manifest entry for the two `.python-version` files.** Holds
  the pair, but not the other pins; one gate for all three decisions is
  what deterministic-guards WS4 planned.

## Workstreams

### 1. The copy, the gate, and CI

`barwise/.python-version`; `check-pins.mjs`; its tests (each finding and
refusal planted red); the npm script, root forwarder and `ci.yml` step;
probes for `node-from-nvmrc` (a workflow's `node-version-file` replaced

environment, which a file edit cannot change); the ADR's Enforced-by and
Consequences; deterministic-guards WS4's status.

## Open decisions (for review)

1. **The runner image.** deterministic-guards WS4 says `runs-on` never
   names a floating image. Pinning it means choosing an Ubuntu version
   in four workflows, which this session cannot confirm against the
   runner GitHub currently serves for `ubuntu-latest`. Recommended: the
   owner picks the image; `check:pins` then adds the rule.
2. **Node patch at pre-push.** CLAUDE.md says coverage thresholds are
   not portable across Node versions, which argues for refusing any
   difference; a developer machine a patch behind would then be blocked
   at push. Recommended: refuse another major, print a patch difference;
   CI runs the exact pin anyway.
3. **Copy or move `.python-version`.** Recommended: the checked copy, as
   above, which needs no decision reworded.

## Risks and testing

- `uv run` in a fresh `ci:local` worktree builds a venv; the readback
  then costs a few seconds once. It uses `--frozen`, per the
  python-from-the-lockfile ADR.
- A machine without uv gets a refusal at pre-push. The session hook
  installs uv; the refusal names it.
