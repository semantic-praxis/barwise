# DDL export writes auto_counter and scale-only decimals so they read back

Status: Implemented 2026-10-03 -- the single workstream

Created: 2026-10-03
Last-updated: 2026-10-03
Tracking: barwise-hgr, barwise-e5n

Two conceptual data types do not survive a DDL export and re-import.
Workstream 3 of `ddl-round-trip-fixed-point.spec.md` left both outside
the DDL loss set, because DDL can carry them and the exporter does not:

- **auto_counter** exports as plain `INTEGER` and reads back as
  `integer` (barwise-hgr). SQL has identity columns.
- **A decimal with a scale and no precision** exports as bare `DECIMAL`
  and reads back with neither (barwise-e5n). SQL cannot state a scale
  without a precision, so the exporter has to choose one.

After this change an auto_counter column exports as
`INTEGER GENERATED BY DEFAULT AS IDENTITY` and reads back as
auto_counter. A scale-only decimal exports as `DECIMAL(38,s)` and reads
back with its scale. The only remaining difference is the precision of
38, which DDL cannot avoid; it is declared in the DDL loss set.

## Principle

**Explicit over implicit.** An identity column is how SQL says "this
number is generated"; writing `INTEGER` drops that statement, and the
importer then cannot recover it. A precision the model did not declare
is invented by the exporter, so the spec names the number and the loss
set declares it, rather than leaving it as an unexplained diff.

**Orthogonality.** Identity is a property of the column that owns the
counter, not of its SQL type string. A foreign key copies the key's
type and must not copy its identity; a dbt, Avro or OpenAPI renderer
reads `Column.dataType` and must not see the DDL clause. So identity
is a separate `Column` field, rendered only by the DDL renderer.

## Decisions (resolved with the requester, 2026-10-03)

- **D1. One ANSI spelling for every dialect.** The DDL export renders
  types the same way for every dialect; only constraints are routed
  per dialect (`dialectCapabilities.ts`: "the spec defers
  dialect-specific types until there is demand"). Identity follows that
  rule: `GENERATED BY DEFAULT AS IDENTITY`, which is SQL:2003 and runs
  on Postgres, Databricks and ANSI. MySQL, Snowflake, Redshift and
  BigQuery spell it differently or lack it, exactly as `UUID` and
  `DATETIME` already differ. Per-dialect type spelling stays deferred.
  `BY DEFAULT` rather than `ALWAYS`, so a load that supplies its own
  ids is not refused.
- **D2. Default precision 38.** It is the widest precision Snowflake,
  SQL Server, BigQuery (NUMERIC) and Postgres all accept, so a value
  that fit the model fits the column. 18 would fit in 8 bytes but can
  overflow; dropping the scale with a warning loses information the
  model stated.

## Requirements

- **R1.** When a column's value type has data type auto_counter, the
  relational mapper shall mark the column `identity: true` and keep its
  `dataType` as `INTEGER`.
- **R2.** When a foreign key copies an identity key's type, the mapper
  shall not mark the foreign key column as identity.
- **R3.** When the DDL renderer writes an identity column, it shall
  write `INTEGER GENERATED BY DEFAULT AS IDENTITY` before any `DEFAULT`
  and `NOT NULL`.
- **R4.** When the DDL importer reads a column with an identity clause -- `GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY [(...)]`,
  `AUTO_INCREMENT`, `AUTOINCREMENT [(...)]`, or `IDENTITY [(...)]` --
  it shall give the column data type auto_counter, and shall read the
  clauses after it (so a following `NOT NULL` is kept). Today each of
  these is reported as "not imported" and ends clause parsing.
- **R5.** A `GENERATED ALWAYS AS (expr)` computed column is not an
  identity and keeps its current "not imported" warning.
- **R6.** When a decimal data type has a scale and no length, the
  mapper shall write `DECIMAL(38,s)`, or `DECIMAL(s,s)` when s is above
  38, since no engine accepts a scale larger than the precision.
- **R7.** The DDL loss set shall declare exactly one new loss: a
  `dataTypeChanged` from a decimal with no length to a decimal of
  length 38. The grader's subset match shall read `null` in a loss-set
  entry as "this field is absent", so the entry cannot also cover a
  decimal whose declared precision changed to 38, and an entry's
  `unchanged` list shall name fields that must be equal on both ends,
  so it cannot cover a scale that changed either.
- **R8.** When a subtype's key becomes the shared key referencing its
  supertype, the mapper shall drop the subtype's own identity: the
  column takes the supertype's value.

## Out of scope

- Per-dialect type spelling (D1), including identity for MySQL,
  Snowflake, Redshift and BigQuery.
- An export annotation saying the precision was defaulted. The default
  is fixed and documented here; an annotation is a follow-up if anyone
  asks for one.
- The dbt importer, which reads `parseSqlDataType` and has no column
  clauses to read.

## Implementation notes

- **Measured on the small trial tier.** After the change, every
  `dataTypeChanged` left in the 12 kernels' DDL round trips is a declared
  loss: money to decimal, other to text, and a scale-only decimal gaining
  precision 38 (C01 DoseAmount; C09 VisitNumber, DoseAmount, LabValue). The
  auto_counter changes (C05 PurchaseOrderItemId and MaterialPlantDataId,
  C06 MovementId) are gone. The 12 round-trip rows still fail with the same
  1,784 deltas outside the loss set and 103 inside: each of these object
  types also loses its definition, which is workstream 4 of
  `ddl-round-trip-fixed-point.spec.md`, so no whole delta moved inside.
- **A table can carry two identity columns.** R1 marks every auto_counter
  column, so a model whose auto_counter value type is both a table's key
  and one of its attributes exports two. Postgres accepts that; SQL:2003
  allows one per table. Two existing mapper test fixtures have this shape
  because their reference-mode fact type has no uniqueness constraint. No
  trial kernel does. Restricting identity to the key would leave a non-key
  counter reading back as integer, so R1 stands.
- **`IDENTITY` as a first type word is still a type.** The shared type
  mapping reads a column typed `IDENTITY` as auto_counter, so the
  importer treats `IDENTITY` as a clause only after the type's first word.
- **Review of PR #586 found three gaps, all fixed in it.** A subtype
  whose own key was auto_counter kept its identity after the key became
  the shared foreign key to its supertype, because `settleSubtypeKey`
  spreads the copied type over the existing column (R8). The precision
  entry did not constrain scale, so a changed scale graded as the
  declared loss (`unchanged` in R7). A scale above 38 rendered as
  `DECIMAL(38,39)` (R6).
