# Eval suite hardening: cases that discriminate above the saturation line

Status: Accepted (implemented with this spec; see Implementation
notes)
Created: 2026-08-09
Last-updated: 2026-08-09
Tracking: follow-up to the saturation finding in
`docs/prompt-eval-sonnet5-2026-08-08.md` and
`docs/agent-eval-2026-08-09.md`; parent spec
`docs/specs/prompt-optimization-harness.spec.md`. No bd issue yet (bd
unavailable in this session).

## Principle

Composability -- the suite is the shared metric every optimization lane
composes against (the scorer, `barwise prompt eval`, the DSPy metric,
the agent evals), and a saturated metric silently stops doing its one
job. In the 2026-08-08/09 runs, Claude Sonnet 5 with the sonnet5-1
variant scored 1.000 on all four seed cases and the measured subagents
clustered at the top; the suite can no longer rank two good prompts.
The fix is data, not code: the scorer, weights, and check machinery
stay untouched, and the suite grows cases whose rubrics reach the
construct territory where extractions actually differ.

The headroom is verified, not guessed: the extraction prompt teaches
objectification, ring, frequency, exclusion, subset, and external
uniqueness, but the four seed cases exercise none of these -- their
rubrics stop at binary fact types, one ternary, subtypes, and
uniqueness/mandatory/value constraints. The check machinery already
reaches further: `forbids_population` supports `value`, `frequency`,
and `ring` (all ring types have population rules and counterexample
generators), and no seed case uses any of the three.

## Scope

In scope (all data plus test updates in `@barwise/promptlab`):

- When the suite is loaded, it shall declare three new cases after the
  existing four: `project-staffing` (ring + frequency),
  `conference-reviews` (objectification + role value constraint), and
  `freight-corrections` (noisy transcript: a mid-conversation
  correction, aliases, a ternary, and explicit example data).
- When a new case's recorded payload is scored, it shall pass its full
  rubric with zero validation errors and zero warnings, and its exact
  score shall be pinned in `tests/scoreExtraction.test.ts`
  (answer-key invariant).
- When a new case declares a reference, the reference shall be
  generated by running the recorded payload through the production
  parse path (`parseExtractionResponse` -> `enforceConformance` ->
  `parseDraftModel` -> `OrmYamlSerializer`), never hand-written.
- When the suite manifest gains cases, its `version` shall bump to
  `1.1.0`, and the loader test shall pin the new version and the
  seven-case id list in declared order.
- When `freight-corrections` is scored, its rubric shall include a
  `forbids_population` frequency check whose bound reflects the
  transcript's corrected figure (the correction supersedes the earlier
  statement), and its recorded payload shall carry at least one
  complete example population instance (guarding the
  `population/incomplete-instance` path end-to-end).

Out of scope, deferred and named:

- Scorer, weights, and check-runner changes: none. Saturation is a
  data problem; `requires_verbalization`'s brittleness (below) is
  accepted, not fixed here.
- New baseline measurements over the grown suite (keyless subagent
  channel or keyed `barwise prompt eval`): a follow-up run, not this
  change. Until then the new cases carry no model scores.
- Gym exercises from the same domains: the gym catalog
  (`packages/learn/exercises/`) is a different audience; nothing there
  changes.
- `populationMapping`'s arity brittleness (matches by player-name
  multiset): known, documented in the harness spec; the new rubrics
  are authored within its limits rather than waiting on a fix.

## Why these three cases

Each case targets a distinct failure surface the 2026-08-08/09 runs
showed or the seed suite cannot see:

- **project-staffing** (ring + frequency). Self-referencing fact
  types are where the baseline runs drifted most (the
  employee-hierarchy manager chain), yet the seed rubrics never test
  ring semantics. A mentoring acyclicity rule and a 1..3 project
  assignment bound make the model state machine-checkable rules the
  prompt explicitly teaches and models routinely omit.
- **conference-reviews** (objectification). The prompt's
  objectification rules (fact type + entity both present, entity gets
  its own reference mode) are multi-part and easy to half-do; a
  half-done objectification breaks identifier constraints and shows
  up in `must_validate` and the uniqueness checks. No seed case
  touches `objectified_fact_types` at all.
- **freight-corrections** (transcript adversity). All four seed
  transcripts are clean single-pass statements; real working sessions
  correct themselves and use synonyms. The rubric encodes the
  corrected frequency bound, so an extraction that anchors on the
  first-stated figure fails a check rather than a vibe. The same case
  carries the suite's first complete example population, closing the
  gap named in the model-lint spec's follow-ups.

## Alternatives considered

- **Harden by re-weighting instead of new cases.** Raising the
  conformance/warning weights would spread today's scores without
  measuring anything new -- the same constructs stay untested, and a
  prompt could recover the loss with formatting alone. Lost.
- **Use `requires_verbalization` for the new rubrics.** It matches a
  whole FORML sentence byte-for-byte (whitespace-normalized), so a
  correct model with a different but valid reading template fails.
  Right tool for the gym (the exercise brief pins the reading), wrong
  tool for extraction, where reading wording is the model's choice.
  The new rubrics stay on `must_validate` / `requires_element` /
  `forbids_population`, which grade semantics.
- **One big case instead of three.** A single kitchen-sink domain
  couples the failure surfaces: a model that fumbles objectification
  would also lose its ring/frequency checks through cascading
  validation errors, and the per-construct signal the delta report
  needs is gone. Three orthogonal cases keep one construct per case
  diagnosable.

## Workstreams (each independently shippable)

### 1. project-staffing

Transcript, answer key, generated reference, rubric (must_validate;
requires_element for Employee, Project, and the self-referencing
mentoring fact type; forbids_population ring on mentoring;
forbids_population frequency on assignment; forbids_population
internal_uniqueness on an identifier). Suite entry + version bump +
test updates land with the first case so the suite is never
half-declared.

### 2. conference-reviews

Transcript, answer key with `objectified_fact_types`, generated
reference, rubric (must_validate; requires_element for the objectified
entity and the underlying fact type; forbids_population
internal_uniqueness on the reviewer-paper pair; forbids_population
value on the score role).

### 3. freight-corrections

Transcript with a correction, aliases, a ternary, and explicit example
data; answer key with a complete population instance; rubric
(must_validate; requires_element; forbids_population
internal_uniqueness composite on the ternary; forbids_population
frequency with the corrected bound).

## Open decisions (for review)

Autonomous session: no requester interview was possible; each
assumption below is stated rather than silently resolved.

- **Case count (assumed: three).** Three orthogonal cases cover the
  verified headroom (ring/frequency, objectification, adversity).
  More cases raise eval cost per run linearly; fewer would leave a
  taught construct unmeasured. Revisit after the next measurement run
  shows whether the suite now separates prompts.
- **Suite version semantics (assumed: minor bump to 1.1.0).** Adding
  cases changes every suite-mean score, so history rows across
  versions are not comparable; the version field is the marker. A
  major bump was reserved for weight or scorer changes.
- **Correction semantics in freight-corrections (assumed: the
  correction wins).** The rubric enforces the corrected bound as the
  single truth. An alternative reading -- flag the conflict as an
  ambiguity instead of resolving it -- was rejected because the
  transcript's correction is explicit ("scratch that"), not a genuine
  conflict; a model that flags it as ambiguity but still constrains
  to the corrected bound passes.

## Risks and testing

- **Answer keys must clear the strictened lint tier.** With
  `validationWarning: 0.05` live, every multi-role fact type in a new
  key needs an internal uniqueness constraint and every population
  instance must be complete, or the pinned score silently dips. The
  keys are scored locally (production parse path) before pinning;
  the pins then guard them in CI.
- **Existing pins must not move.** No code changes and no edits to
  the four seed cases; `scoreExtraction.test.ts` keeps the current
  four rows byte-identical, extended by three.
- **Ring/frequency checks depend on counterexample generation.**
  Verified before authoring: all eight ring types and frequency have
  generators and population rules; the rubric fails loudly
  ("unsupported constraint shape") rather than silently passing if a
  shape regresses.
- Full gate: `npx vitest run` in `packages/promptlab`, then the
  monorepo build/test from `barwise/`.

## Non-goals

- No change to scorer, weights, check runners, or the gym evaluator.
- No new check kinds; `requires_verbalization` stays unused for
  extraction rubrics (see Alternatives).
- No re-measurement in this change; the suite grows first, models get
  scored against it in a follow-up run.

## Implementation notes (2026-08-09)

Every `forbids_population` check in the new rubrics was
mutation-tested: the answer key passes it, and a payload stripped of
the constraint under test fails it. That battery forced three
corrections to the brief -- all instances of one mechanism, **masking**:
a check passes for the wrong reason when a rule other than the one
under test rejects the injected population.

- **conference-reviews swapped its mandatory check for uniqueness.**
  The mandatory counterexample needs the constrained entity to play a
  role in some other fact type (to build "exists but does not
  participate"), and Review's only other involvement is the
  objectification link, which is not a role. The generator refuses
  loudly rather than guessing; the rubric now probes uniqueness on the
  score instead.
- **project-staffing dropped the ProjectName mandatory from its
  answer key.** With it, any injected assignment population was
  rejected by `population/mandatory-violation` (minted Projects have
  no names), so the frequency check passed with or without a
  frequency constraint. Removing the mandatory from the key (the
  rubric never tested it) restored the frequency check's signal.
- **project-staffing swapped its mentor-uniqueness check.** With the
  ring constraint present, the two-mentors counterexample was
  rejected by the ring rule, masking a missing uniqueness constraint.
  The check moved to `Project has ProjectName`, where nothing else
  can reject the injected population.
- **Known limit, accepted:** the value counterexample mints a token
  (`ReviewScore#invalid`) outside ANY enumerated set, so the value
  check detects a missing value constraint but cannot distinguish a
  looser one (values 1-6 also rejects the token). Sharpening the mint
  to probe boundary values is a core follow-up, not a suite change.

The first measurement run (2026-08-09, keyless channel) surfaced a
fourth authoring rule the mutation battery cannot catch: **every name
a rubric references must be transcript-derivable.** All three measured
configs objectified conference-reviews correctly but named the score
value type from their own vocabulary (`Score`, `OverallScore`) because
the transcript said only "overall score"; the rubric's
`requires_element` and population mapping match by player name, so a
legitimate naming choice failed three checks. Fixed by pinning the
stakeholder term in the transcript ("that is our term for the overall
rating"), which turns the checks into a fair test of following
stakeholder language. Answer-key pin unchanged (0.96).

Final pins: project-staffing 0.98 (1 correction), conference-reviews
0.96 (2), freight-corrections 0.94 (3) -- all warning-free under the
lint tier. Existing four pins unmoved.
