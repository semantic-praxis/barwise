# Comparable eval splits: rate-based penalties and cases stratified across train and dev

Status: Draft for review (design only -- no implementation in this PR)
Created: 2026-08-24
Last-updated: 2026-08-24
Tracking: barwise-844, barwise-845, barwise-846. Parent
`docs/specs/prompt-optimization-harness.spec.md`; corrects a split
decision made in `docs/specs/eval-metric-readiness.spec.md` and a
deferral made in `docs/specs/eval-transcript-realism.spec.md`.
Evidence: the three paid compilations recorded in
`docs/specs/dspy-optimizer.spec.md`.

## Principle

Composability -- the suite is the shared metric every optimization lane
composes against, and it is mismeasuring in two independent ways.
`runSuite({split})` promises one measurement over two disjoint samples,
so a lane may compile on train and read dev as generalization. It does
not deliver that. Train and dev differ on transcript length, on
transcript style, and on the rubric vocabulary itself: the seven train
cases carry fourteen `forbids_population` checks between them and the
three dev cases carry none. A prompt tuned against constraint semantics
is then scored on element recall. That is not a held-out sample; it is a
different metric wearing the same name, which is the exact failure
`loadSuite.ts:210-213` names when it bounds `collapseFloor` below 1.

Underneath that sits a second defect with the same shape. Score is a
rubric fraction normalised to [0, 1] minus penalties counted absolutely,
so the penalty side scales with model size and the reward side does not.
The dev transcripts are ten times longer than the train transcripts,
produce models several times larger, and are charged per occurrence for
it. The result is not a harsh score, it is a meaningless one: three of
the four recorded compilation arms floored at zero, where
`scoreExtraction` clamps and every difference below the clamp is
discarded.

Both defects push the same way, which is why they were invisible
separately. Fixing the dataset without fixing the metric moves the
flooring to whichever cases are largest. Fixing the metric without
fixing the dataset leaves an unfloored number that still compares two
different rubrics.

## Is the dev split held out, or is it a different test? (resolved: a different test)

A different test. The three dev cases were added by
`eval-transcript-realism.spec.md` workstream 2 to introduce multi-party
disagreement, and they became the entire dev split in the same change.
Every property that made them worth adding is therefore also a property
that distinguishes dev from train, and nothing separates the two
intentions in the record.

Measured across the ten cases as they stand:

| Axis                 | train (7 cases) | dev (3 cases)  |
| -------------------- | --------------- | -------------- |
| Transcript length    | 154-243 words   | 2,163-2,967    |
| Speakers             | facilitator + 1 | 3 or more      |
| Reference model      | all seven       | none           |
| `forbids_population` | 14 total        | 0              |
| `requires_ambiguity` | 0               | 2 (in 2 cases) |
| `requires_element`   | 2-3 per case    | 4-5 per case   |
| Reference fact types | 2-10 (median 3) | not generated  |

The rubric row is the decisive one, and it is not a matter of degree.
`forbids_population` is the only check in the vocabulary that tests
whether a constraint actually forbids what it should: the evaluator
derives a counterexample population from the reference model and
requires the candidate to reject it. It exists in train and nowhere
else. `requires_element` tests that a named type or fact type is
present. So train grades constraint semantics and dev grades element
recall, and a change that improves one is under no obligation to
improve the other.

That is what the mipro compilation produced and what was misread at the
time. Its own metric rose 50.89 to 52.97 on the compile set while every
held-out figure fell, and the reading recorded was "the split caught an
optimizer overfitting". The split may well have caught that; it cannot
be used as evidence of it, because the two numbers were never measuring
one quantity. The correct statement is weaker and more useful: the run
established that the two splits disagree, and nothing about which one is
right.

The dev cases also carry no reference model, which is not an oversight
but a consequence -- references are generated by running a recorded
payload through `parseExtractionFromJson`, and no payload has ever been
recorded for these three (`vendor-onboarding.eval.yaml:7-9` says so).
That is why they have no `forbids_population` checks: the check needs a
reference, `loadSuite.ts:131-136` refuses a case that declares one
without it, and so the rubric was authored around the gap.

The gap is cheap to close and closing it is separable from everything
else here, which is why it is workstream 2 rather than part of the
re-split.

## Should the penalty be a count or a rate? (resolved: a rate)

A rate. The current score is

```
score = rubricPassed / rubricTotal - sum over rules of (weight * occurrences)
```

where the first term is bounded to [0, 1] by construction and the second
is unbounded and grows with the size of the model. Two cases with the
same defect _rate_ therefore receive different scores according to how
much domain the transcript described, and the larger one can be charged
more than a point for defects that afflict a fixed fraction of its
elements.

The arithmetic is available from the recorded runs rather than
hypothetical. On the dev split, `structural/binary-missing-inverse-reading`
occurred at a measured mean of 10.67 per scored run; at
`validationWarning: 0.05` that single rule costs 0.53. The train
reference models hold a median of 3 fact types in total, so the same
rule at a 100% defect rate costs a median train case 0.15. Same defect
rate, 3.5x the charge, decided entirely by transcript length. The two
figures are not symmetric, and the asymmetry runs in the safe
direction: 0.53 is what a dev case was _measured_ to pay, while 0.15 is
the _most_ a median train case could ever pay for that rule. So 3.5x is
a floor on the gap, not an estimate of it. Add
`completeness/fact-type-without-constraints` (2.0 to 5.5 per run across
the recorded arms) and the remaining tallies, and the dev cases clear
1.0 in penalties without any statement having been made about how good
the extraction was.

Above 1.0 the clamp in `scoreExtraction` takes over, and its damage is
the real cost. Every arm past the clamp reports 0.000, so runs that
differ substantially compare equal; and because the clamped values are
identical, the sample SD collapses and `resolvableDifference` shrinks
with it, so a meaningless margin can clear a threshold the flooring
itself manufactured. The optimizer lane already refuses to read a
saturated comparison (`SATURATION_SHARE`, `export.py`), which contains
the damage without addressing it: a guard that fires on three arms out
of four is describing a broken metric, not protecting a working one.

Rating the penalties defines the failure out of existence rather than
guarding it. The proposed form divides each rule's occurrences by the
size of the model it was measured on:

```
penalty(rule) = weight(rule) * occurrences(rule) / max(elementCount, 1)
elementCount  = objectTypes + factTypes
```

The weight then means something a reviewer can hold: _the cost of a
model in which every element carries this kind of defect_. Under the
current form a weight means the cost of one occurrence, which is only
interpretable once you know how many occurrences are possible -- and
that number is different for every case.

Two properties fall out and both are worth stating because they are what
make the change safe. The answer-key invariant survives untouched: a
recorded answer key produces zero occurrences, zero over any denominator
is still zero, and all seven keys still score exactly 1.000. And the
per-rule tallies in `CaseScore` are unaffected -- rating changes what the
score charges, not what the record names, so the rule counts the delta
reports lean on stay exactly as legible as they are now.

The weights must be re-fitted in the same change, because their meaning
changes. That is a re-baselining of every score, which is what the major
version bump is for.

## Scope

In scope:

- When `scoreExtraction` charges a penalty for a rule, the system shall
  divide that rule's occurrence count by the scored model's element
  count before applying the weight.
- When a scored model has no elements, the system shall charge no
  size-rated penalty rather than dividing by zero.
- When the seven recorded answer-key payloads are scored under the new
  weights, the system shall report exactly 1.000 for each, unchanged.
- When a case declares a `forbids_population` check, the system shall
  find a generated reference model for it; the three dev cases shall
  gain recorded payloads and generated references so that they can.
- When the suite manifest assigns splits, each split shall contain at
  least two cases of each size class and shall draw on the same check
  vocabulary, so that a mean over one split is comparable to a mean over
  the other. A **short** case is one whose transcript runs under 500
  words and a **long** case one over 1,500; the current ten fall either
  side of that gap with nothing between, and a case authored into the
  gap belongs to whichever class the reviewer assigns it in the
  manifest.
- When the suite composition or the penalty form changes, the manifest
  version shall move to 2.0.0 and the delta report shall refuse to
  compare across the bump.

Out of scope, deferred and named:

- Rewriting the seven existing transcripts. They stay as authored; the
  re-split moves cases between halves and adds new ones, it does not
  re-author old ones.
- The `collapseFloor` value. It was fitted to seven cases of pre-2.0.0
  evidence (`suite.yaml:31-37` says to revisit it once ten have run) and
  rating the penalties changes the distribution it sits in. Re-fitting
  it needs the workstream 4 baseline, so it is that workstream's
  output, not this spec's input.
- Review-surface evals. Specified separately in
  `docs/specs/review-surface-evals.spec.md`.
- Any transcript derived from client material. The exclusion recorded
  in `eval-transcript-realism.spec.md` stands and this spec promotes it
  to a stated rule (see Open decisions).

The saturation guard stays deliberately. It is the record of what a
broken metric looked like, it costs nothing when the metric is sound,
and a guard that never fires is the outcome this spec is aiming at
rather than a reason to delete it.

`evals/history.jsonl` does not exist in the repository, and this changes
the cost of the re-split materially. `historyPathFor` resolves it beside
the manifest, `provenance.ts:57` records that it is untracked, and no
run has ever written one here. The continuity that
`eval-metric-readiness.spec.md` cited as the reason to keep the seven in
train ("their scores form the entire recorded history") lives only in
operators' local files. So the re-split is nearly free today and gets
monotonically more expensive the moment harness workstream 3 lands the
first committed rows. That is an argument for doing it now, and it is
the anchor most likely to be wrong by the time this is implemented --
check it again before starting.

## Target architecture

```
suite.yaml  (2.0.0)
  weights:                       meaning changes: cost at a 100% defect rate
    conformanceCorrection        rated over elementCount
    validationError              rated over elementCount
    validationWarning            rated over elementCount
    ambiguityExcess              unrated -- a budget overrun is already a rate
  splits:
    train: [ ... ]               both splits stratified over size class
    dev:   [ ... ]               and drawing on the same check vocabulary

scoreExtraction(payload, case, weights) -> CaseScore
  parse payload -> ExtractionResponse
    |-- model half    -> enforceConformance -> parseDraftModel
    |                    -> evaluateCandidate(GymCheck subset)
    |-- payload half  -> runPromptChecks(PromptCheck subset)
    `-- fold:
          rubricPassed / rubricTotal
          - sum over rules of weight * occurrences / max(elementCount, 1)
          - ambiguityExcess * excess
          clamped at 0                    <- should now be unreachable in practice

CaseScore  gains  elementCount            <- the denominator, recorded
           keeps  warningsByRule, errorsByRule, correctionsByCategory
                                          <- raw counts, unchanged and still primary
```

`elementCount` is recorded on `CaseScore` rather than recomputed by
readers, for the reason `MetricLog.scored` exists: a denominator that
each consumer derives for itself is a denominator two consumers will
eventually derive differently. The delta report and the history row take
it from the score.

## Alternatives considered

- **Cap the total penalty below 1.0** (say at 0.9) so the rubric
  fraction always survives. Rejected: it relocates the clamp rather
  than removing it, and it makes every sufficiently bad model score
  0.1 -- the same collapse of distinguishability one notch up. It also
  leaves the size bias fully intact, which is the actual defect.
- **Report the rubric fraction and the penalty as two numbers and never
  combine them.** Honest, and rejected on composability: DSPy, the
  history file, and `resolvableDifference` all consume a scalar, and
  handing three consumers a pair means three places decide how to
  collapse it. That is the change-amplification shape. The pair already
  exists for the question it answers well -- `collapseFloor` splits
  survival from quality -- and this is a different question.
- **Rate by a per-rule denominator** (each rule divided by the
  population it could fire on: binary fact types for
  `binary-missing-inverse-reading`, fact types for
  `fact-type-without-constraints`). More correct, and rejected for now
  on orthogonality: it requires promptlab to know each validator rule's
  firing population, which couples the scorer to the rule set and makes
  every new rule a promptlab change. Carried in Open decisions, because
  the single denominator is an approximation and a reviewer should get
  to weigh that.
- **Leave the metric and only fix the dataset.** Rejected on the
  measured evidence: the flooring is driven by model size, so it would
  reappear on whichever new cases are largest, and the new realistic
  cases are exactly the large ones.
- **Leave the dataset and only fix the metric.** Rejected: an unfloored
  score still compares constraint semantics against element recall. The
  numbers would become readable and stay incomparable, which is worse
  than obviously broken.
- **Move the three realism cases into train and hold out three of the
  short clean ones.** Cheap, and rejected: it inverts the confound
  rather than removing it, and it throws away the property those three
  cases were authored for by tuning against them.

## Workstreams (each independently shippable)

### 1. Rate the penalties (code only)

Change the fold in `scoreExtraction` to divide occurrences by
`elementCount`, add `elementCount` to `CaseScore`, and re-fit the four
weights in `suite.yaml` under their new meaning. No case file changes,
no split changes.

The acceptance criterion is the answer-key invariant: all seven recorded
payloads still score exactly 1.000, which holds by construction because
they produce no occurrences. That makes this the smallest blast radius
of the three data-affecting changes, and it is why it goes first --
every later workstream wants to read scores that are not floored.

The suite bumps to 2.0.0 here, since the scale of every non-perfect
score changes. Splitting the bump across workstreams would put two
incomparable meanings under one version.

Mutation check: invert the denominator (multiply instead of divide) and
confirm the pinned scores move; a test that only asserts 1.000 passes
under any denominator, since zero occurrences hide the arithmetic
entirely. Pin at least one non-perfect score with a hand-built payload
so the rate is asserted rather than assumed.

### 2. Give the three realism cases a reference and the full rubric (data only)

Record an extraction payload for `vendor-onboarding`,
`subscription-billing`, and `incident-response`; generate their
`.reference.orm.yaml` files through `parseExtractionFromJson` per the
package's standing rule; add `forbids_population` checks where the
transcript settles a constraint, and a `requires_ambiguity` check to
`incident-response`, which has none despite being a realism case.

This closes the vocabulary half of the confound without touching the
split assignment, so it is separable from workstream 3 and worth landing
first: it is the cheapest step that makes the two halves comparable at
all.

Needs a key, or a payload recorded by hand from a session model. Both
paths are keyless-compatible downstream -- the payload is a recorded
artifact and the scorer that grades it makes no call.

### 3. Stratify the splits and add cases (data; provisional: not yet grounded)

Author new long transcripts so that each split carries cases of both
size classes, then reassign splits so train and dev are two samples of
one population. The deficit is smaller than it looks: the suite already
holds seven short cases and three long ones, so the minimum
stratification (two of each class per split) needs exactly **one** new
long case. How many beyond that, and which domains, is an Open
decision; the structural requirement is that neither split be
identifiable from its rubric or its transcript length.

Provisional because the number of new cases needed depends on the
dispersion measured after workstream 1, which is not yet observable.
Ground it against that baseline before authoring.

### 4. Re-baseline, re-fit the collapse floor, and record (needs a key)

Run the 2.0.0 suite for the default artifact and both committed variants
at repeat >= 5, on both splits, and write the first committed rows of
`evals/history.jsonl`. Re-fit `collapseFloor` against that distribution
rather than against the seven-case evidence it was fitted to. Last,
because everything before it is verifiable without a key.

## API and migration impact

- `@barwise/promptlab` public API widens: `CaseScore` gains
  `elementCount`. An addition, so existing callers keep compiling.
- The meaning of `SuiteWeights` fields changes without their types
  changing, which no compiler will catch. The version bump is the only
  signal, which is an argument for landing the re-fitted defaults in
  `loadSuite.ts` in the same commit as the fold, so a manifest omitting
  a weight cannot silently inherit a count-era default.
- `@barwise/cli` needs no change; `prompt eval` and `prompt score`
  print what `CaseScore` carries.
- `optimizer/` needs no change. `metric.py` reads `score` and the rule
  tallies, both of which keep their shapes. Its saturation guard should
  stop firing, and if it does not, workstream 1 did not work.
- Every recorded score, in any local history file or any dated document
  under `docs/`, becomes incomparable to anything measured after the
  bump. The delta report already refuses a cross-version comparison.

## Open decisions (for review)

- **The re-fitted weight values.** The form is settled; the numbers are
  not. Recommend `validationWarning: 0.4`, `validationError: 0.8`,
  `conformanceCorrection: 0.2` -- read as "a model in which every
  element carries a warning loses 0.4". The alternative is to fit them
  so a median train case scores roughly what it does today, which
  preserves intuition about the scale at the cost of choosing weights
  to flatter a number rather than on their meaning. Recommend against.
- **Single denominator or per-rule denominators.** Recommend the single
  `elementCount` denominator for this change: it removes the size bias,
  costs one field, and keeps the scorer ignorant of the validator's rule
  semantics. It is an approximation -- a rule that can only fire on
  binary fact types is rated against a denominator including value types
  -- so a reviewer who wants per-rule denominators should say so now,
  because retrofitting them is a second re-baselining.
- **How many new cases, and which domains.** The minimum is one new
  long case: two short and two long per split needs four of each, and
  the suite holds seven short and three long. Recommend three new long
  cases instead, giving train four short plus three long and dev three
  short plus three long -- a dev half of six cases rather than four, at
  three transcripts of authoring. The minimum is a defensible trade if
  authoring is the constraint -- it still widens dev from three cases to
  four and makes both halves comparable, which is the whole point; the
  extra two buy a tighter dev mean, not a different conclusion. Domains
  are open; the constraint is that they be invented and mutually
  distinct.
- **Whether `ambiguityExcess` stays unrated.** Recommend yes: it is
  charged against a per-case declared budget, so it is already a rate
  against an authored denominator, and rating it again would double-
  count. Named because it is the one weight this change leaves alone
  and that asymmetry should be a decision rather than an oversight.
- **Promoting the client-material exclusion to a stated rule.**
  Recommended in `eval-transcript-realism.spec.md` and never resolved.
  Eval content is checked in and published in the npm package.
  Recommend writing "no client-derived material in `evals/`" into
  `packages/promptlab/CLAUDE.md` as part of workstream 3.

## Risks and testing

- **Risk: the re-fitted weights are chosen to produce a comfortable
  number.** Guard: choose them from the stated meaning before running
  the baseline, record the chosen values in the manifest comment with
  that reasoning, and treat a post-baseline adjustment as a further
  version bump rather than a tweak.
- **Risk: rating hides a genuinely bad large model.** A model that
  invents forty elements, half of them defective, now scores like a
  model that invents four with two defects. That is the intended
  behaviour for defect _rate_ and it does leave volume unpunished.
  Guard: the rubric fraction already punishes invention indirectly
  (invented elements do not satisfy `requires_element` checks), and
  `elementCount` is recorded on `CaseScore`, so an arm inflating its
  denominator is visible in the record. Tripwire: if a candidate's mean
  `elementCount` rises materially and its score rises with it, the denominator
  is being gamed and needs a bound.
- **Risk: the answer-key invariant passes vacuously.** Zero occurrences
  divided by anything is zero, so the seven pinned 1.000 scores cannot
  detect a wrong denominator. Guard: the mutation check in workstream 1
  and at least one pinned non-perfect score.
- **Risk: workstream 2's recorded payloads bake in one model's
  behaviour.** The references are generated from whatever payload is
  recorded, so a weak extraction becomes the reference. Guard: the
  existing rule that a recorded payload must pass its case's full
  rubric, applied before generating the reference, plus a read-through
  of each generated reference against its transcript.
- **Risk: `history.jsonl` gains committed rows before the re-split
  lands**, making workstream 3 expensive after this spec argued it was
  cheap. Tripwire: if harness workstream 3 lands first, re-open the
  ordering here.
- **Testing:** every workstream but 4 is offline. The scorer change is
  a pure function and gets direct tests over hand-built payloads at
  known element counts. `promptEvalOffline.test.ts` continues to drive
  the whole command against the fake provider. No live call enters CI.

## Non-goals

- No change to the scorer's determinism contract: same payload, case,
  and weights still give a byte-identical `CaseScore`.
- No change to the rubric fraction, the check vocabulary, or
  `evaluateCandidate`.
- No change to `@barwise/learn`, `@barwise/llm`, or `@barwise/core`.
- No new CLI commands or flags.
- No judge, no LLM in the scoring path, no network in any test.
- No re-authoring of the seven existing transcripts.
